# CashSight — Architecture

## Pipeline

```
Ledger + Settlements + Bank Statement (CSV)
              │
              ▼
   backend/reconciliation/pipeline.py
   ├── bank_matcher.py       (Step 1: settlement → bank txn, by UTR + window + tolerance)
   ├── subset_sum_matcher.py (Step 2: settlement → ledger orders, by combination search)
   ├── ambiguity_resolver.py (decides: resolved / ambiguous / unresolved)
   └── orphan_checker.py     (Step 3: bank txns with no settlement link)
              │
              ▼
      { matches: [...], exceptions: [...] }
              │
       ┌──────┴──────┐
       ▼             ▼
  backend/score.py   backend/forecasting/forecast_pipeline.py
  (reads answer_key)  (uses reconciliation's own exceptions
                        as the "pending" settlement set)
```

## The integrity guarantee

**`backend/reconciliation/*` never imports `backend/score.py` or
`data/ground_truth/answer_key.json`, directly or indirectly.**

This is not a style choice — it's the difference between a system that
genuinely discovers which ledger orders back a settlement, and one that
reads the answer off a label. Concretely:

- `settlements.csv` (generated by `data_gen/generate_settlements.py`)
  contains **no `order_ids` field**. The only way `subset_sum_matcher.py`
  can find that a settlement is backed by orders ORD-102 + ORD-103 is by
  searching combinations of ledger orders in a date window until one
  sums to the settlement's `gross_amount` within tolerance.
- The ledger (`data_gen/generate_ledger.py`) deliberately includes
  distractor orders and, for `ambiguous_batch` cases, a second valid
  combination of orders that sums to the same target — planted by
  `data_gen/inject_anomalies.py` — so the search is genuinely contested,
  not trivially unique.
- `data/ground_truth/answer_key.json` (written by
  `data_gen/build_answer_key.py`) is read by exactly one file in the
  whole backend: `backend/score.py`. You can verify this yourself:
  `grep -r answer_key backend/reconciliation/` returns nothing.

## Why the engine sometimes refuses to answer

`ambiguity_resolver.py` implements one rule: if `subset_sum_matcher.py`
finds more than one combination of orders that validly sums to a
settlement's amount, the engine does **not** guess — it flags
`ambiguous_batch` for human review. This was added after testing showed
that guessing (picking any valid combination) silently produces
false-positive matches that inflate accuracy numbers without being
correct. Refusing to guess is what makes the reported precision/recall
trustworthy.

## Why the forecast is "scenario-based," not predictive

`backend/forecasting/risk_profile.py` assigns settlement-outcome
probabilities from a small, hand-set lookup table
(`backend/config.py::RISK_BASE_RATES`), not from any measured real-world
data. The dataset itself is synthetic. Every place this matters says so
explicitly — including the `assumption_note` string returned by
`/api/forecast` itself — so nobody mistakes a demo assumption for a
claim about Razorpay's actual settlement behavior.

## What still works if you delete a whole file

- Delete `backend/explain.py` → `/api/reconcile`, `/api/score`, and
  `/api/forecast` are unaffected. Only `/api/explain` returns a 503.
- Delete `data/ground_truth/answer_key.json` → `/api/reconcile` and
  `/api/forecast` are unaffected. Only `/api/score` fails (it needs
  ground truth to score against, by design).
